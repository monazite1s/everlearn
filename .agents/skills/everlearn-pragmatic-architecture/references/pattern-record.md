# 设计模式记录

仅在确实引入设计模式时填写。

| 项目     | 内容                               |
| -------- | ---------------------------------- |
| 模式     | 标准模式名称                       |
| 位置     | 主要类、函数或模块                 |
| 问题     | 已确认且直接实现无法妥善解决的问题 |
| 角色     | 模式参与者与各自职责               |
| 代价     | 新增间接层、状态、运行或测试成本   |
| 边界     | 不允许该模式扩散到的范围           |
| 移除条件 | 可以恢复为直接实现的明确条件       |
| 验证     | 证明模式解决问题的测试或运行证据   |

主要实现符号使用：

    @designPattern Adapter — 隔离供应商 SDK，领域层只依赖稳定端口。

不要把框架依赖注入、普通接口、文件夹分层或单一策略函数登记为模式。

## 架构债红线

以下结构性约束不可违反；命中即视为架构债，必须修复或记录为待办，不得静默放行。

- 禁止职责重叠的组件库或框架并存；同一职责只保留一个已批准实现。
- 迁移 DDL 必须事务原子化；多语句迁移包在单个事务中。
- 服务端运行时配置单一来源；API 与 Worker 不得逐字复制同一份校验逻辑。
- 端口与宿主来自环境变量，禁止硬编码监听地址。
- 禁止空壳包；每个 package 必须有明确激活里程碑与首个真实内容。
